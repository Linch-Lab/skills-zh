雙軸審查 `HEAD` 與使用者提供的固定點之間的 diff：

- **標準**——程式碼是否符合此 repo 文件中記錄的編碼標準？
- **規格**——程式碼是否忠實實作了原始 issue / PRD / 規格？

兩個軸以平行子 agent 執行，避免互相污染上下文，然後此 skill 彙總其發現。

議題追蹤系統應已提供——若 `docs/agents/issue-tracker.md` 不存在，執行 `/setup-matt-pocock-skills`。

## 流程

### 1. 確定固定點

使用者說的任何東西都是固定點——commit SHA、分支名稱、標籤、`main`、`HEAD~5` 等。若未指定，詢問。

擷取 diff 指令一次：`git diff <fixed-point>...HEAD`（三點，因此比較對象是 merge-base）。也記錄 commit 清單：`git log <fixed-point>..HEAD --oneline`。

繼續之前，確認固定點可解析（`git rev-parse <fixed-point>`）且 diff 非空。

### 2. 找出規格來源

按以下順序尋找原始規格：

1. Commit 訊息中的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等）——透過 `docs/agents/issue-tracker.md` 中的工作流程取得。
2. 使用者作為參數傳入的路徑。
3. `docs/`、`specs/` 或 `.scratch/` 下符合分支名稱或功能的 PRD/規格檔案。
4. 若找不到，詢問使用者規格在哪。若他們說沒有，規格子 agent 將跳過並回報「無規格可用」。

### 3. 找出標準來源

Repo 中任何記錄程式碼應如何撰寫的文件，如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除 repo 記錄的內容外，標準軸始終攜帶下方的氣味基線——一組固定的 Fowler 程式碼氣味（《重構》第 3 章），即使在 repo 無記錄時也適用。兩條規則約束它：

- **Repo 覆蓋。** 記錄的 repo 標準始終優先；若它認可基線會標記的東西，抑制該氣味。
- **永遠是判斷。** 每個氣味是標籤化的啟發式（「可能的 Feature Envy」），絕非硬性違規——且，如此處任何標準，跳過工具已強制執行的東西。

每個氣味讀作：它是什麼 → 如何修復；對 diff 進行比對：

- **Mysterious Name**——函式、變數或型別名稱未揭示其功能或內容。→ 重新命名；若想不到誠實的名稱，設計本身有問題。
- **Duplicated Code**——相同邏輯形狀出現在變更中多個區塊或檔案。→ 提取共享形狀，從兩處呼叫。
- **Feature Envy**——方法訪問另一個物件的資料多於自己的。→ 將方法移到它羨慕的資料上。
- **Data Clumps**——相同幾個欄位或參數總是一起出現。→ 捆綁為一個型別，傳遞它。
- **Primitive Obsession**——原始型別或字串代理一個值得擁有自己型別的領域概念。→ 給該概念自己的小型別。
- **Repeated Switches**——對相同型別的相同 switch/if-cascade 在變更中反覆出現。→ 用多型取代，或兩處共享一個映射。
- **Shotgun Surgery**——一個邏輯變更迫使在 diff 中對多個檔案進行分散編輯。→ 將一起變更的東西集中到一個模組。
- **Divergent Change**——一個檔案或模組因多個不相關的原因被編輯。→ 拆分使每個模組因一個原因而變更。
- **Speculative Generality**——為規格沒有的需求添加的抽象、參數或鉤子。→ 刪除；往回內聯直到真正需求出現。
- **Message Chains**——呼叫者不應依賴的長 `a.b().c().d()` 導航。→ 將走訪隱藏在第一個物件的一個方法背後。
- **Middle Man**——一個類別或函式大部分只是轉發委派。→ 砍掉它，直接呼叫真正的目標。
- **Refused Bequest**——子類別或實作者忽略或覆蓋了大部分繼承的內容。→ 放棄繼承，使用組合。

### 4. 平行啟動兩個子 agent

發送一則訊息，包含兩個 Agent 工具呼叫。兩者皆使用 `general-purpose` 子 agent。

**標準子 agent prompt**——包含：

- 完整 diff 指令和 commit 清單。
- 步驟 3 中找到的標準來源檔案清單，加上步驟 3 的氣味基線全文貼上——子 agent 沒有其他方式存取它。
- 任務：「回報——每個相關檔案/區塊——(a) diff 中違反記錄標準的每個地方：引用標準（檔案 + 規則）；以及 (b) 你發現的任何基線氣味：命名它並引用區塊。區分硬性違規和判斷——記錄標準的違反可以是硬性的，但基線氣味永遠是判斷，且記錄的 repo 標準覆蓋基線。跳過工具已強制執行的東西。400 字以內。」

**規格子 agent prompt**——包含：

- diff 指令和 commit 清單。
- 規格的路徑或取得的內容。
- 任務：「回報：(a) 規格要求但缺失或不完整的需求；(b) diff 中存在但未被要求的行為（範圍蔓延）；(c) 看似已實作但實作方式錯誤的需求。每項發現引用規格行。400 字以內。」

若規格缺失，跳過規格子 agent 並在最終報告中註明。

### 5. 彙總

在 `## Standards` 和 `## Spec` 標題下呈現兩份報告，逐字或輕微清理。不要合併或重新排序發現——兩個軸刻意分開（見為何雙軸）。

結尾一行摘要：每軸總發現數，以及每軸內最嚴重的問題（若有）。不要選出跨軸的單一贏家——那正是分離想要避免的重新排序。

## 為何雙軸

一個變更可以通過一軸而不通過另一軸：

- 遵循每條標準但實作了錯誤的東西 → 標準通過，規格失敗。
- 完全做到 issue 要求的但違反專案慣例 → 規格通過，標準失敗。

分開報告阻止一軸掩蓋另一軸。
