# 診斷 Bug

一個針對困難 bug 的紀律。僅在明確有理由時跳過階段。

探索程式碼庫時，閱讀 `CONTEXT.md`（若存在）以獲得相關模組的清晰心智模型，並檢查你所觸及區域的 ADR。

## 階段 1——建立回饋循環

**這就是核心技能。** 其他都是機械性的。如果你有一個針對此 bug 的緊密通過/失敗信號——一個在此 bug 上會紅燈的信號——你就會找到原因；二分法、假設檢驗和檢測都只是消耗它。如果沒有，盯著程式碼看再多也沒用。

在這裡投入不成比例的努力。**積極、有創意、拒絕放棄。**

### 建構方法——按以下順序嘗試

1. **失敗測試** 在能觸及 bug 的任何接縫上——單元、整合、端對端。
2. **Curl / HTTP 腳本** 對運行中的開發伺服器。
3. **CLI 呼叫** 使用固定輸入，與已知良好的快照比較 stdout。
4. **無頭瀏覽器腳本**（Playwright / Puppeteer）——驅動 UI，對 DOM/console/network 進行斷言。
5. **重播擷取的追蹤。** 將真實網路請求/負載/事件日誌儲存到磁碟；隔離重播到程式碼路徑中。
6. **拋棄式 harness。** 啟動系統的最小子集（一個服務、模擬依賴），用單一函式呼叫執行 bug 程式碼路徑。
7. **屬性/模糊循環。** 若 bug 是「有時輸出錯誤」，執行 1000 次隨機輸入尋找失敗模式。
8. **二分 harness。** 若 bug 在兩個已知狀態之間出現（commit、資料集、版本），自動化「在狀態 X 啟動、檢查、重複」以便 `git bisect run`。
9. **差異循環。** 對舊版本 vs 新版本（或兩個配置）執行相同輸入，比較輸出。
10. **HITL bash 腳本。** 最後手段。若必須由人類點擊，用 `scripts/hitl-loop.template.sh` 驅動他們，使循環仍保持結構化。擷取的輸出回饋給你。

建立正確的回饋循環，bug 就 90% 修好了。

### 收緊循環

將循環視為產品。一旦有了一個循環，收緊它：

- 能更快嗎？（快取設定、跳過不相關的初始化、縮小測試範圍。）
- 信號能更清晰嗎？（對具體症狀斷言，而非「沒當機」。）
- 能更確定性嗎？（固定時間、種子 RNG、隔離檔案系統、凍結網路。）

一個 30 秒的 flaky 循環幾乎和沒循環一樣；一個 2 秒的確定性循環是緊密的——除錯超能力。

### 非確定性 bug

目標不是乾淨重現，而是更高的重現率。觸發循環 100 次、平行化、增加壓力、縮小時間窗口、注入 sleep。50% flaky 的 bug 可除錯；1% 不可——持續提高重現率直到可除錯。

### 當你真的無法建立循環時

停下來明確說明。列出你嘗試了什麼。向使用者請求：(a) 能重現它的環境存取權，(b) 擷取的工件（HAR 檔案、日誌 dump、core dump、帶時間戳的螢幕錄影），或 (c) 允許添加暫時的生產檢測。不要在沒有循環的情況下繼續進行假設。

### 完成條件——一個紅燈的緊密循環

階段 1 完成條件：循環緊密且可紅燈：你能說出一個指令——一個腳本路徑、一個測試呼叫、一個 curl——你已經至少執行過一次（貼上呼叫和輸出），且：

- [ ] 可紅燈——它驅動實際的 bug 程式碼路徑並對使用者的確切症狀斷言，因此能在此 bug 上紅燈、修復後綠燈。不是「運行無錯誤」——必須能捕捉這個特定 bug。
- [ ] 確定性——每次執行相同結果（flaky bug：固定的高重現率，如上）。
- [ ] 快速——秒級，非分鐘級。
- [ ] Agent 可執行——你可無人值守運行。

如果你發現自己在建立理論之前讀程式碼，停下來——直接跳到假設正是此技能要防止的確切失敗。沒有紅燈指令，沒有階段 2。

## 階段 2——重現並最小化

執行循環。看到它紅燈——bug 出現。

確認：

- [ ] 循環產生了使用者描述的失敗模式——不是碰巧在附近的另一個失敗。錯誤的 bug = 錯誤的修復。
- [ ] 失敗可跨多次執行重現（或對非確定性 bug，重現率足夠高）。
- [ ] 你已擷取確切症狀（錯誤訊息、錯誤輸出、慢速計時）以便後續階段驗證修復。

### 最小化

一旦紅燈，將重現縮小到仍會紅燈的最小場景。逐一削減輸入、呼叫者、配置、資料和步驟，每次削減後重新執行循環——只保留對失敗有影響的東西。

為何要這樣做：最小重現縮小了階段 3 的假設空間（更少的可疑移動部件），並成為階段 5 的乾淨回歸測試。

完成條件：每個剩餘元素都是有影響的——移除任何一個都會使循環變綠燈。

## 階段 3——假設

在測試任何假設之前產生 3–5 個排名假設。單一假設生成會錨定在第一個看似合理的想法上。

每個假設必須可證偽：陳述它做出的預測。

> 格式：「若 <X> 是原因，則 <改變 Y> 會使 bug 消失 / <改變 Z> 會使其更糟。」

若無法陳述預測，假設只是感覺——丟棄或銳化它。

測試前向使用者顯示排名清單。他們通常有能立即重新排名的領域知識。

## 階段 4——檢測

每個探測必須對應階段 3 的特定預測。一次改變一個變數。

工具偏好：

1. 除錯器 / REPL 檢查（若環境支援）。一個斷點勝過十行日誌。
2. 在區分假設的邊界處的針對性日誌。
3. 永遠不要「記錄所有東西然後 grep」。

用唯一前綴標記每個除錯日誌，例如 `[DEBUG-a4f2]`。清理時一個 grep 搞定。

效能分支：對於效能回歸，日誌通常是錯的。改為建立基準測量（計時 harness、`performance.now()`、分析器、查詢計畫），然後二分。先測量，後修復。

## 階段 5——修復 + 回歸測試

在修復之前寫回歸測試——但僅當有正確的接縫時。

正確的接縫是測試在呼叫點發生的真實 bug 模式的地方。若唯一可用的接縫太淺，那裡的回歸測試給出虛假信心。

若無正確接縫存在，那本身就是發現。記錄下來。程式碼庫架構正在阻止鎖定此 bug。為下一個階段標記。

若有正確接縫存在：

1. 將最小化的重現轉為該接縫上的失敗測試。
2. 看到它失敗。
3. 套用修復。
4. 看到它通過。
5. 對原始（未最小化）場景重新執行階段 1 回饋循環。

## 階段 6——清理 + 事後分析

宣布完成前必須：

- [ ] 原始重現不再重現（重新執行階段 1 循環）
- [ ] 回歸測試通過（或接縫缺失已記錄）
- [ ] 所有 `[DEBUG-...]` 檢測已移除（grep 前綴）
- [ ] 拋棄式原型已刪除（或移至明確標記的除錯位置）
- [ ] 被證明正確的假設在 commit / PR 訊息中陳述——讓下一個除錯者學到

然後問：什麼能防止此 bug？若答案涉及架構變更，交接給 `/improve-codebase-architecture` skill 並附上具體細節。在修復完成後提出建議，而非之前——你現在比開始時有更多資訊。
