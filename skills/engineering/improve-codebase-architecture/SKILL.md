# 改善程式碼庫架構

浮現架構摩擦並提出深化機會——將淺模組轉為深模組的重構。目標是可測試性和 AI 可導航性。

此指令由專案的領域模型提供資訊，並建立在共享的設計詞彙上：

- 執行 `/codebase-design` skill 取得架構詞彙（模組、介面、深度、接縫、適配器、槓桿、局部性）及其原則。在每個建議中精確使用這些術語。
- `CONTEXT.md` 中的領域語言為好的接縫命名；`docs/adr/` 中的 ADR 記錄此指令不應重新訴訟的決策。

## 流程

### 1. 探索

先界定範圍再掃描。深化模組透過使未來對它的變更更容易來回報，因此對最近變更過的程式碼庫部分給予額外權重。

- 若使用者指定了方向，採用它。
- 否則，走訪 commit 歷史尋找熱點，讓這些路徑先行吸引你的注意力。

先閱讀專案的領域詞彙表（`CONTEXT.md`）和所觸及區域的 ADR。

然後使用 Explore 子 agent 走訪程式碼庫。有機探索並注意你遇到摩擦的地方：

- 哪裡理解一個概念需要在許多小模組之間跳轉？
- 哪裡模組是淺的——介面幾乎和實作一樣複雜？
- 哪裡純函式只是為了可測試性而提取，但真正的 bug 隱藏在它們如何被呼叫中？
- 哪裡緊密耦合的模組跨接縫洩漏？
- 哪些部分未經測試，或難以透過當前介面測試？

對任何你懷疑是淺的東西套用刪除測試。

### 2. 以 HTML 報告呈現候選者

將 HTML 寫入 OS 暫存目錄。使用 Tailwind CDN 佈局和樣式，Mermaid CDN 繪製圖形關係的圖表。每個候選者有前後視覺化。

每個候選者一張卡片：

- 檔案、問題、解決方案、效益（以局部性和槓桿解釋）、前後圖表、推薦強度標記

結尾一個頂部推薦區段。

詳見 HTML-REPORT.md。

不要在此時提出介面。檔案寫完後問使用者想探索哪一個。

### 3. 詰問循環

使用者選定候選者後，執行 `/grilling` skill 走訪決策樹。決策結晶時內嵌產生副作用——執行 `/domain-modeling` skill 保持領域模型最新。
