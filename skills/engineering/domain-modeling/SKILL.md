# 領域建模

在設計過程中積極建立並打磨專案的領域模型。這是主動的紀律——挑戰術語、發明邊界案例場景、在概念成形的那一刻立即寫下詞彙表和決策。（僅僅閱讀 `CONTEXT.md` 取得用語不屬於此 skill——那是任何 skill 都能做的一行習慣。此 skill 用於你正在改變模型時，而非僅消費它。）

## 檔案結構

大多數 repo 為單一情境：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

若根目錄存在 `CONTEXT-MAP.md`，則 repo 有多個情境。地圖指向每個情境的位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系統層級決策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 情境特定決策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

延遲建立檔案——只在有內容可寫時才建立。若尚無 `CONTEXT.md`，在第一個術語確定時建立。若尚無 `docs/adr/`，在需要第一份 ADR 時建立。

## 對話期間

### 以詞彙表挑戰

當使用者使用的術語與 `CONTEXT.md` 中現有語言衝突時，立即指出。「你的詞彙表將『取消』定義為 X，但你似乎指的是 Y——是哪一個？」

### 打磨模糊語言

當使用者使用模糊或過載的術語時，提出一個精確的標準術語。「你說『帳戶』——是指 Customer 還是 User？它們是不同的東西。」

### 討論具體場景

當討論領域關係時，以具體場景進行壓力測試。發明探測邊界案例的場景，迫使使用者對概念之間的界線保持精確。

### 與程式碼交叉比對

當使用者陳述某個東西如何運作時，檢查程式碼是否一致。若發現矛盾，立即提出：「你的程式碼會取消整個 Order，但你剛才說部分取消是可行的——哪個才對？」

### 內嵌更新 CONTEXT.md

當術語確定時，立即更新 `CONTEXT.md`。不要批次處理——在發生當下就捕捉。使用 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) 中的格式。

`CONTEXT.md` 必須完全不包含實作細節。不要將 `CONTEXT.md` 當作規格書、草稿紙或實作決策的存放處。它是詞彙表，僅此而已。

### 節制地提供 ADR

僅在以下三個條件全部成立時才提議建立 ADR：

1. **難以逆轉**——之後改變心意的成本是顯著的
2. **缺乏上下文會令人困惑**——未來的讀者會想知道「為什麼他們這樣做？」
3. **真實取捨的結果**——確實存在替代方案，而你基於特定理由選擇了其中一個

若三者缺一，跳過 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。
