# ADR 格式

ADR 存放在 `docs/adr/` 中，使用連續編號：`0001-slug.md`、`0002-slug.md` 等。

延遲建立 `docs/adr/` 目錄——僅在需要第一份 ADR 時建立。

## 模板

```md
# {決策的簡短標題}

{1-3 句話：背景是什麼、我們決定了什麼、以及為什麼。}
```

就這樣。一份 ADR 可以只是一個段落。價值在於記錄決策已經做出以及為什麼——而非填滿各個區段。

## 可選區段

僅在它們增加真正價值時才加入。大多數 ADR 不需要它們。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）——當決策被重新檢視時有用
- **Considered Options**——僅在被拒絕的替代方案值得記住時
- **Consequences**——僅在需要指出非顯著的下游影響時

## 編號

掃描 `docs/adr/` 找出最高現有編號，加一。

## 何時提議建立 ADR

以下三個條件必須全部成立：

1. **難以逆轉**——之後改變心意的成本是顯著的
2. **缺乏上下文會令人困惑**——未來的讀者看到程式碼會想「他們到底為什麼這樣做？」
3. **真實取捨的結果**——確實存在替代方案，而你基於特定理由選擇了其中一個

若決策容易逆轉，跳過——你只會把它逆轉回來。若不令人困惑，沒有人會好奇為什麼。若沒有真正的替代方案，除了「我們做了顯而易見的事」之外沒什麼好記錄的。

### 什麼符合資格

- **架構形狀。** 「我們使用 monorepo。」「寫入模型是事件溯源，讀取模型投影到 Postgres。」
- **情境之間的整合模式。** 「Ordering 和 Billing 透過領域事件通訊，而非同步 HTTP。」
- **帶有鎖定效應的技術選擇。** 資料庫、訊息匯流排、驗證提供者、部署目標。不是每個函式庫——只是那些需要一季才能換掉的。
- **邊界和範圍決策。** 「客戶資料由 Customer 情境擁有；其他情境僅以 ID 引用。」明確的不做和明確的要做一樣有價值。
- **刻意偏離顯而易見路徑的決策。** 「我們使用手寫 SQL 而非 ORM，因為 X。」任何合理讀者會假設相反的決策。這些能阻止下一位工程師「修正」一個刻意的選擇。
- **程式碼中不可見的約束。** 「我們不能使用 AWS，因為合規要求。」「回應時間必須在 200ms 以下，因為合作夥伴 API 合約。」
- **拒絕不顯然的替代方案。** 若你考慮過 GraphQL 但基於微妙理由選擇了 REST，記錄下來——否則六個月後又會有人提議 GraphQL。
