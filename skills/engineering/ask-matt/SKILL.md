# Ask Matt

你不會記得每個 skill，所以問。

**流程（flow）** 是穿越各 skills 的路徑。大多數路徑沿著一條**主流程**和兩條**匝道**匯入。其他都是獨立 skill，或運行在下層的詞彙層。

## 主流程：想法 → 交付

大多數工作走的路徑。你有一個想法，想把它做出來。

1. **`/grill-with-docs`** — 透過詰問打磨想法。當你**有程式碼庫**時從這裡開始：它是有狀態的，將學到的內容保留在 `CONTEXT.md` 和 ADR 中。（沒有程式碼庫？用 `/grill-me`——見獨立 skill。兩者都運行相同的 `/grilling` 原始操作；`grill-with-docs` 會留下書面記錄。）
2. **分支——能否在對話中解決所有問題？** 若某個問題需要可執行的答案（狀態、業務邏輯、必須親眼看到的 UI），繞道經過原型，由 `/handoff` 雙向橋接（見跨對話）：
   - `/handoff` 出去，然後針對該檔案開啟新對話，
   - `/prototype` 用拋棄式程式碼回答問題，
   - `/handoff` 把你學到的傳回來，並從原始想法討論串引用。
3. **分支——這是多對話的建構嗎？**
   - **是** → `/to-spec`（將討論串轉為規格書），然後 `/to-tickets` 拆成曳光彈票據，每張票據宣告其**阻塞邊**。本地追蹤系統下每張票據一個檔案在 `.scratch/<feature>/issues/`，手動按阻塞者優先處理；在真實追蹤系統上，邊變成原生阻塞連結，任何阻塞者已完成的票據都可以領取——對每張票據啟動 `/implement`，**每張之間清除上下文**。
   - **否** → 在這裡直接用 `/implement`，在同一上下文視窗內。

   無論哪種，`/implement` 內部驅動 `/tdd` 來建構每個 issue——一次一個紅綠切片——然後以 `/code-review` 收尾，對 diff 進行雙軸審查（標準 + 規格），最後提交。當你只想以測試優先方式建構具體行為而不需要完整規格時，單獨使用 `/tdd`；當你想對分支或 PR 進行審查時，單獨使用 `/code-review`。

### 上下文衛生

將步驟 1–3 保持在**一個不中斷的上下文視窗**中——在 `/to-tickets` 之前不要壓縮或清除——讓詰問、規格和票據都建立在相同的思維上。每個 `/implement` 則從票據開始全新上下文。

此限制取決於**智慧區間**：模型仍能清晰推理的視窗（頂尖模型約 120K token）。若對話在 `/to-tickets` 之前逼近此限制，不要勉強在降級狀態下繼續——用 `/handoff` 在新討論串中繼續。

## 匝道

產生工作、然後匯入主流程的起始情境。

- **Bug 和請求堆積** → `/triage`。它將 issue 移過分類角色，產出 agent-ready 的 issue，之後由 `/implement` 領取。分類僅適用於**不是你建立的** issue——bug 回報、外來功能請求、任何原始進來的東西。`/to-tickets` 產出的票據已經是 agent-ready，所以不要對它們分類。
- **東西壞了** → `/diagnosing-bugs`。用於困難的 bug：一眼看不出來的、間歇性出現的、在兩個已知良好狀態之間悄悄出現的回歸。它在擁有**緊密回饋循環**之前拒絕推理——一個在此 bug 上已經紅燈的指令——然後以回歸測試修復。其事後分析在真正發現是「沒有好的接縫來鎖定 bug」時，交接給 `/improve-codebase-architecture`。
- **巨大、模糊的工作——全新專案或超大功能建構，超出單一對話** → `/wayfinder`，這裡認知負荷最重的流程。當從這裡到目的地的路徑還看不見時，它在議題追蹤系統上繪製**共享地圖**的**決策票據**，逐一解決——產出**決策，而非交付物**——直到迷霧退去、路徑清晰。`/grill-with-docs` 打磨你能在單一對話中掌握的想法，wayfinder 則用於你無法掌握的——它更慢更密集，所以只用在這種情況，永遠不要用在範圍明確的功能上。當地圖清晰後，它交接，不建構：匯入主流程的 `/to-spec`，將地圖的連結決策坍縮為可建構的計畫，然後照常 `/to-tickets` 和 `/implement`。直接將地圖餵給 `/implement` 會跳過坍縮並丟棄連結細節——只有在工作確實很小的情況下才直接進 `/implement`。

## 程式碼庫健康

非功能工作——維護。

- **`/improve-codebase-architecture`** — 有空時執行，保持程式碼庫對 agent 友善。它浮現深化機會；挑選一個會產生一個想法，可以帶入主流程的 `/grill-with-docs`。它是找到候選者的調查；`/codebase-design`（下方）是你設計所選候選者的工作檯。

## 底層詞彙

兩個 model-invoked 參考，運行在其他 skills 之下——各自是其詞彙的唯一真相來源。當問題是詞語而非流程時直接使用；或讓上方 skills 自行引入。

- **`/domain-modeling`** — 打磨專案的領域語言：挑戰模糊術語、解析過載詞語、將難以逆轉的決策記錄為 ADR。它是 `/grill-with-docs` 驅動的主動紀律，保持 `CONTEXT.md` 為乾淨的詞彙表。
- **`/codebase-design`** — 深度模組詞彙（模組、介面、深度、接縫、適配器、槓桿、局部性），用於設計模組的形狀：在乾淨接縫上的小介面背後承載大量行為。`/tdd` 和 `/improve-codebase-architecture` 都使用它。

## 跨對話

- **`/handoff`** — 當討論串已滿或需要分支出去（例如進入 `/prototype` 對話）時，將對話壓縮為 markdown 檔案。你不在原地繼續——你開啟新對話並引用該檔案來攜帶上下文。它是上下文視窗之間的橋樑，雙向皆可。在想要全新對話但需要保留當前對話時使用。
- **`/compact`**（內建）— 留在同一個對話中，讓前面的回合被摘要。在階段之間的有意中斷處使用，當你不介意失去逐字歷史時。不要在階段中途壓縮——agent 可能迷失方向。`/handoff` 分岔；`/compact` 繼續。

## 獨立 Skill

完全不在主流程上。

- **`/grill-me`** — 與 `/grill-with-docs` 相同的持續詰問，但用於你沒有程式碼庫時。無狀態：不儲存任何東西到本地，不建立 `CONTEXT.md`。用於打磨任何不在 repo 中的計畫或設計。
- **`/prototype`** — 一個小型拋棄式程式，回答一個設計問題：這個狀態模型感覺對嗎，這個 UI 該長什麼樣子。從第一天就是拋棄式——保留答案，刪除程式碼。它是主流程步驟 2 的繞道，但任何時候設計問題難以在紙上解決時都可以使用。
- **`/research`** — 將閱讀工作委派給背景 agent：它針對主要來源調查問題，然後在 repo 中留下一份有引用的 Markdown 檔案。在它閱讀時繼續工作。它產出的檔案是帶入主流程 `/grill-with-docs` 的東西——研究餵養思考，而非取代思考。
- **`/teach`** — 跨多個對話學習一個概念，使用當前目錄作為有狀態的工作區。
- **`/writing-great-skills`** — 撰寫和編輯 skills 的參考指南。

## 前置條件
