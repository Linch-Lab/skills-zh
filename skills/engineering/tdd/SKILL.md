# 測試驅動開發

TDD 是紅燈 → 綠燈的循環。此 skill 是讓這個循環產出值得保留的測試的參考：什麼是好的測試、測試放在哪裡、反模式、以及循環的規則。每個章節在每次循環都適用——在循環前和循環中參考，而非循環後。

探索程式碼庫時，閱讀 `CONTEXT.md`（若存在），讓測試名稱和介面用語與專案的領域語言一致，並尊重你所觸及區域的 ADR。

## 什麼是好的測試

測試透過公開介面驗證行為，而非實作細節。程式碼可以完全重寫；測試不應該變。一個好的測試讀起來像規格——「使用者可以用有效購物車結帳」精確告訴你有什麼功能——並且在重構後存活，因為它不在乎內部結構。

範例見 [tests.md](tests.md)，模擬指南見 [mocking.md](mocking.md)。

## 測試切入點——測試放在哪裡

**測試切入點（seam）** 是你測試所在的公開邊界：你在此觀察行為而不深入內部。測試存在於測試切入點上，永遠不對內部實作測試。

**只在預先約定的測試切入點上測試。** 在撰寫任何測試之前，先寫下要測試的切入點並向使用者確認。未經確認的切入點上不寫任何測試。你無法測試所有東西——事先約定切入點是讓測試精力落在關鍵路徑和複雜邏輯上、而非每個邊界案例的方法。

提問：「公開介面是什麼？我們應該測試哪些切入點？」

## 反模式

- **耦合實作**——模擬內部協作者、測試私有方法、或透過側通道驗證（查詢資料庫而非使用介面）。特徵：重構時測試掛了但行為沒變。
- **套套邏輯**——斷言用跟程式碼相同的方式重新計算預期值（`expect(add(a, b)).toBe(a + b)`、用同樣方式手算的 snapshot、常數斷言等於自己），因此測試在構造上就成立，永遠不可能與程式碼不一致。預期值必須來自獨立的真相來源——已知的正確字面值、人工計算的範例、規格。
- **水平切片**——先寫完所有測試，再寫所有實作。批量測試驗證的是想像中的行為：你測試的是東西的形狀而非使用者可見的行為，測試對實際變更不敏感，且在理解實作之前就綁定了測試結構。改用**垂直切片**——一個測試 → 一個實作 → 重複，每個測試都是一顆**曳光彈**，回應上一個循環教你的東西。

## 循環的規則

- **紅燈在綠燈之前。** 先寫失敗的測試，然後只寫足夠讓它通過的程式碼。不要預期未來的測試或添加推測性功能。
- **一次一個切片。** 每次循環一個切入點、一個測試、一個最小實作。
- **重構不屬於此循環。** 它屬於審查階段（見 `code-review` skill），而非紅燈 → 綠燈的實作循環。
